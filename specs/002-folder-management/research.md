# 技術調査と設計決定 (Research & Design Decisions): フォルダ管理と一括オープン

**機能ブランチ**: `002-folder-management`  
**日付**: 2026-11-08  
**対象**: ブックマークのフォルダ分け・プレフィックス階層化および一括オープン機能

---

## 1. フォルダ表現方式（プレフィックス方式）とデータ抽出アルゴリズム

### 決定 (Decision)
既存のストレージデータ構造 `Record<string, BookmarkEntry[]>` をそのまま維持し、ニックネーム文字列内に含まれるスラッシュ `/`（例: `work/gh`, `work/jira`, `infra/aws/console`）をパス風の階層区切りとして動的に解釈する。

フォルダ抽出のロジック：
- 各ニックネーム `key` を `/` で分割（split）する。
- 最後のスラッシュより前の部分（例: `work/jira` の場合は `work`、`infra/aws/console` の場合は `infra` および `infra/aws`）をフォルダプレフィックスとして抽出。
- 抽出されたすべてのフォルダプレフィックスをユニーク化（Set）してフォルダ一覧を導出する。

### 根拠 (Rationale)
1. **完全な後方互換性**: 既存の `bookmarks` データスキーマやバックアップ JSON の形式を破壊しない。
2. **ストレージ容量効率**: Chrome Sync ストレージの 100KB 容量制限に対して、メタデータ（フォルダ定義用オブジェクトやIDマップなど）の追加オーバーヘッドがゼロ。
3. **キーボードフレンドリー**: ユーザーは従来のテキスト入力のみで自然にフォルダ階層を構築・管理できる。

### 代替案の検討 (Alternatives Considered)
- **代替案 A: 独立したフォルダデータ構造（例: `folders: { id: string, name: string, parentId?: string }`）**:
  - 却下理由: ストレージ同期の容量制限（100KB）を圧迫し、移行マイグレーション処理や既存 JSON インポート/エクスポートの後方互換性維持が極めて複雑化するため。
- **代替案 B: BookmarkEntry 内に `folder` プロパティを追加**:
  - 却下理由: Nickmark はニックネーム単位で複数の URL を持つ構造であり、ニックネームとフォルダの所属が不整合になるリスクがあるため。

## 2. オムニボックスにおけるサジェストと一括オープン実行アーキテクチャ

### 決定 (Decision)
オムニボックス（`chrome.omnibox`）での入力処理（`onInputChanged` / `onInputEntered`）において、フォルダ一致を以下のように処理する。

1. **通常モード（`nm`）**:
   - `nm <prefix>/`（末尾スラッシュ入力時）:
     - ユーザーの意図が「フォルダ一括オープン」であると判定し、最上位（デフォルト候補）に「📁 `<prefix>/` の全ブックマークを一括オープン（Nタブ）」を設定。Enter キーで即時実行。
   - `nm <prefix>`（末尾スラッシュなし）:
     - 配下の個別ブックマーク（`work/gh` 等）を通常通り優先表示しつつ、サジェストリスト内にフォルダ一括オープン候補（`📁 <prefix>/ (Nタブを一括で開く)`）を提示。
2. **コマンドモード（`:open` / `:o`）**:
   - `:open <prefix>` または `:open <prefix>/` で、前方一致する全ニックネームの URL を一括展開。

### 根拠 (Rationale)
末尾スラッシュの有無で「個別ブックマークを開きたい」のか「フォルダ配下を一括で開きたい」のかを自然に識別でき、誤爆を防ぎながら最速のキーストロークで一括起動できる（憲章原則 I に完全合致）。

### 代替案の検討 (Alternatives Considered)
- **コマンドモード限定**:
  - 却下理由: 一括オープンのたびに毎回 `:open ` とタイプするのはキーストロークが多く、日常の作業環境立ち上げにおけるテンポを損なうため。

## 3. 安全上限（閾値）と確認フロー（Service Worker での非同期確認）

### 決定 (Decision)
1. **設定値の保持**:
   - `chrome.storage.local` に `maxBatchOpenTabs`（デフォルト: `20`、範囲: 1〜100）を保存。
2. **上限以下の動作**:
   - 自動的にバックグラウンドタブ（`active: false`）ですべての URL を順次開く（重複 URL は除外、ブックマークレットはスキップ、動的 URL はフォールバック展開）。
3. **上限超過時の動作（21件以上）**:
   - **オムニボックスからの実行時**:
     - Service Worker は直接 `window.confirm` を呼び出せないため、アクティブタブ上に `chrome.scripting.executeScript` を用いて軽量な確認モーダル／プロンプトを注入。
     - ユーザーが「開く」をクリックすると、`chrome.runtime.sendMessage` で Service Worker に承認が伝達され、一括オープンを実行。
     - スクリプト注入不可ページ（`chrome://` 等）の場合は、`list.html?confirmBatchOpen=...` のように一覧画面を開いて確認ダイアログを表示する。
   - **管理画面からの実行時**:
     - PrimeVue の `ConfirmDialog` を使用してモーダル表示し、ユーザーが承認した後に実行。

### 根拠 (Rationale)
ブラウザが一瞬でフリーズ・強制終了するのを確実に防止し、Manifest V3 の Service Worker 制約下でも堅牢にユーザー承認を得られる設計。

## 4. 管理画面（List.vue）でのフォルダ操作とリネーム・一括削除

### 決定 (Decision)
1. **フォルダ絞り込み**:
   - 既存の `DataTable` 上部に PrimeVue の `Select`（ドロップダウン）または `SelectButton` を配置。
   - オプション: `[すべて (ALL), 未分類, フォルダ1, フォルダ2, ...]`。
2. **フォルダ一括オープンボタン**:
   - フォルダ選択時に横に「一括オープン」ボタン（アイコン `pi pi-external-link`）を表示。
3. **フォルダの一括リネーム**:
   - フォルダ横の編集アイコンからダイアログを表示。
   - 変更前のプレフィックス `oldFolder/` を含む全ニックネームを `newFolder/` に一括置換して保存。
4. **フォルダの一括削除**:
   - フォルダ横のゴミ箱アイコンから確認ダイアログ（PrimeVue `ConfirmDialog`）を表示し、対象フォルダ配下のニックネームを一括削除。

### 根拠 (Rationale)
プレフィックス方式における唯一の運用課題（名前変更時に各ブックマークを手動で書き換える手間）を完全に解消し、本格的なフォルダシステムと同等の管理性を実現する。

## 5. 多言語対応および設定画面（Preferences.vue）

### 決定 (Decision)
1. **メッセージ定義**:
   - `package/_locales/ja/messages.json` および `en/messages.json` に、フォルダ絞り込み、リネーム、一括オープン、上限設定、確認メッセージに関するすべてのキーを追加。
2. **設定画面 UI**:
   - `Preferences.vue` に「一括オープンの安全上限件数 (Safety Limit for Batch Open)」項目を追加。PrimeVue の `InputNumber`（min: 1, max: 100）を用いて直感的に設定可能にする。
