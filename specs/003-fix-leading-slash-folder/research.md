# 技術調査と設計決定 (Research & Design Decisions): 先頭スラッシュ付きフォルダ指定の正規化と認識バグ修正

**機能ブランチ**: `003-fix-leading-slash-folder`  
**日付**: 2026-11-09  
**対象**: 先頭スラッシュや連続スラッシュを含むニックネーム・フォルダ指定の正規化、管理画面フィルタ、オムニボックス検索、オートコンプリート補完の一貫性確保

---

## 1. バグの根本原因分析 (Root Cause Analysis)

現在のコードベース（`src/background.ts`, `src/List.vue`, `src/Popup.vue`）を調査した結果、「先頭にスラッシュを入れるとフォルダで絞り込んだときに認識されない」問題は、以下の複数の箇所で先頭スラッシュの扱いが統一されていないことに起因していることが判明しました。

1. **`extractFolders`（`src/background.ts`）における空文字フォルダ生成とパスのズレ**:
   - `nickname.split('/')` をそのまま実行しているため、例えばニックネームが `/work/gh` の場合、`parts` が `["", "work", "gh"]` となる。
   - その結果、`i = 0` で空文字 `""` のフォルダが生成され、`i = 1` でも `currentPath` が `""`（falsy）のため `"work"` が生成されるが、`depth` がずれるほか、`/work` のように1階層のみのつもりのニックネーム（`["", "work"]`）から空文字 `""` フォルダが誤生成される。
2. **管理画面 `List.vue` の `filteredBookmarks` における文字列一致の不一致**:
   - フォルダ選択時、`item.nickname === folderPath || item.nickname.startsWith(folderPath + '/')` で判定している。
   - `folderPath` が `"work"` のとき、ニックネームが `"/work/gh"` だと `"work/"` で始まらないため、**`work` フォルダで絞り込んだ際に一覧に一切表示されない**。
   - また、「未分類（ルート）」選択時も `!item.nickname.includes('/')` で判定しているため、`"/gh"` のような項目がルートにも現れない。
3. **オムニボックス検索・フォルダ一括オープン・コマンドモード（`src/background.ts`）での先頭スラッシュ未除去**:
   - `handleRegularSearchSuggestions` および `onInputEntered` では、末尾のスラッシュのみ `.replace(/\/+$/, '')` で除去しており、先頭のスラッシュを除去していない。そのため、`nm /work/` や `nm /work` と入力すると `folders.get("/work")` を探してしまい、`"work"` フォルダが認識されない。
   - `resolveRegularSearchMatches` でも `firstToken` の先頭スラッシュが除去されないため、`nm /work` で `work/gh` が前方一致（Tier 2）にならず、部分一致（Tier 3）または不一致に落ちてしまう。
   - `:open /work`、`:add`、`:rm` などのコマンド引数や、管理画面・ポップアップの AutoComplete（`searchNewBookmarkNicknames`, `searchNicknames`）でも、先頭スラッシュを入力すると `folder.toLowerCase().startsWith(query)` がマッチしなくなる。
4. **登録・編集時のニックネーム未正規化**:
   - `List.vue`（新規追加・編集・JSON編集）、`Popup.vue`、`background.ts`（`:add`, `:addall`）では `.trim()` のみを行っており、先頭・末尾のスラッシュや連続スラッシュ（`//`）を除去していないため、不整合なキーがそのままストレージに保存されてしまう。

---

## 2. 設計選択肢の比較 (Design Alternatives Comparison)

この問題を解決するため、以下の 3 つの設計アプローチを比較検討しました。

### 選択肢 A: UI の絞り込み・検索時の比較処理のみ都度スラッシュを無視する（局所対応）
- **概要**: ストレージ内のデータ（`/work/gh` 等）や登録処理には手を加えず、`List.vue` のフィルタ判定やオムニボックスの検索比較時にのみ先頭スラッシュを無視して比較する。
- **メリット**:
  - 既存の保存データ書き換えが発生しない。
- **デメリット**:
  - ストレージ内に `/work/gh` と `work/gh` という実質同じニックネームが別キーとして重複登録できてしまい、スコア更新や削除・リネーム時にデータの分裂・不整合が起きる。
  - 比較箇所ごとに正規化漏れが起きやすく、保守性が低い。

### 選択肢 B: 登録・保存時のみスラッシュを除去する（入力ゲート制限のみ）
- **概要**: 新規登録・編集時に先頭・末尾のスラッシュを除去して保存するようにし、検索クエリ側や既存データのロード処理は変更しない。
- **メリット**:
  - 今後の新規登録データはきれいになる。
- **デメリット**:
  - 既に `/work/gh` のように登録されてしまっている既存データのバグが解消されない。
  - ユーザーがオムニボックスやオートコンプリートで検索・絞り込みをする際に、先頭に `/` を付けて `/work/` や `:open /work` と入力したケースで依然としてフォルダが認識されない。

### 選択肢 C（採用）: 共通パス正規化関数の導入 ＋ データ読み書き時の正規化・統合 ＋ 検索・補完クエリ正規化（ハイブリッド一貫正規化）
- **概要**:
  1. `src/background.ts` に共通の正規化ヘルパー関数 `normalizeNicknamePath(raw: string): string`（空白トリム、先頭・末尾の `/` 除去、連続する `//` を単一の `/` に正規化）を定義してエクスポートする。
  2. **データ層の正規化**: `loadBookmarksData` / `saveBookmarksData`（および登録・編集・リネーム・削除・JSON編集）でキーを `normalizeNicknamePath` で正規化する。万が一既存データで `/work/gh` と `work/gh` が両方存在する場合は、同一 URL の重複を除きつつエントリ配列を安全にマージする。
  3. **フォルダ抽出・操作の正規化**: `extractFolders`、`openFolderUrls`、`renameFolder`、`deleteFolder`、`List.vue` の `filteredBookmarks` で正規化パスを使用する。
  4. **検索・補完クエリの正規化**: オムニボックス通常検索（`nm /work/`、`nm /work`）、コマンドモード（`:open /work`、`:add`、`:rm`）、および `List.vue` / `Popup.vue` の AutoComplete クエリにおいて、先頭スラッシュや連続スラッシュが入っていても正規化してフォルダ・ニックネームと照合する。
- **メリット**:
  - 「先頭スラッシュ付きで登録した場合」も「先頭スラッシュ付きで検索・フォルダ絞り込みした場合」も「既に先頭スラッシュ付きデータが保存されている場合」も、すべての経路で 100% 一貫してフォルダが認識される。
  - `/work/gh` と `work/gh` の二重登録・分裂を根本から防止できる。
  - 正規化ロジックを単一の純粋関数 `normalizeNicknamePath` に集約するため、仕様変更やテストが容易で型安全性・保守性が高い。
- **デメリット**:
  - データ読み込み・保存箇所と検索クエリ解析箇所の双方に正規化関数を適用する必要がある（ただし変更箇所は明確で影響範囲も限定的）。

---

## 3. 採用した決定と技術的根拠 (Decision & Technical Rationale)

- **決定**: **選択肢 C（共通パス正規化関数の導入 ＋ データ層・検索クエリ層のハイブリッド一貫正規化）** を採用する。
- **技術的根拠**:
  - Nickmark 憲章の **原則 I（キーボードファースト・オムニボックス中心設計）** および **原則 IV（型安全性とモジュール間共有）** に照らし、`src/background.ts` で正規化関数を一元定義して全画面・バックグラウンドで共有するのが最も堅牢であるため。
  - また、**原則 II（ハイブリッドストレージの安全性）** の観点からも、読み込み・保存時に既存データのエントリを欠損なく正規化・マージすることで、ユーザーの既存ブックマーク資産を一切損なわずにバグを解消できるため。
